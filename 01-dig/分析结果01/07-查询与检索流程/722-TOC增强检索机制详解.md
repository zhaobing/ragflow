## 📋 概述

`retrieval_by_toc()` 是 RAGFlow 系统中的**TOC（Table of Contents，目录）增强检索功能**，利用文档的结构化目录信息来提升检索精度。该功能通过理解文档的层级结构，发现初始检索遗漏的相关内容，特别适合结构化文档（如技术手册、学术论文、书籍等）的检索场景。

### 在检索流程中的位置

```
完整的检索流程：

┌─────────────────────────────────────────────────────────┐
│ 1. 初始检索阶段                                          │
│    - 用户查询 → Elasticsearch/Infinity                  │
```

## 🎯 核心业务价值

### 为什么需要TOC增强检索？

1. **初始检索的局限性**
   - 基于向量/关键词的检索可能遗漏相关内容
   - 无法理解文档的结构和逻辑关系
   - 难以发现跨章节的相关信息

2. **TOC结构的优势**
   - **结构化信息**：反映文档的层级组织
   - **语义丰富**：章节标题高度概括内容
   - **全局视图**：提供文档的整体脉络
   - **层级关系**：父子章节的包含关系

3. **典型应用场景**
   - **技术手册**：查找特定功能或API
   - **学术论文**：定位研究方法或实验结果
   - **培训材料**：发现相关主题的所有章节
   - **法规文档**：检索相关条款和规定

### 步骤1: 选择最相关文档 (649-656行)

```python
idx_nms = [index_name(tid) for tid in tenant_ids]
ranks, doc_id2kb_id = {}, {}
for ck in chunks:
    if ck["doc_id"] not in ranks:
        ranks[ck["doc_id"]] = 0
    ranks[ck["doc_id"]] += ck["similarity"]
    doc_id2kb_id[ck["doc_id"]] = ck["kb_id"]
```

**为什么选择相似度总和最高的文档？**

1. **聚焦最相关文档**
   - 假设最相关的信息集中在少数文档中
   - 避免分散注意力

2. **性能考虑**
   - 只处理一个文档的TOC
   - 减少LLM调用和计算开销

3. **实际效果**
   - 如果问题涉及多个文档，可以通过多轮检索处理
   - 单文档场景下效果最佳

**`relevant_chunks_with_toc()` 函数详解**：

**文件位置**: [rag/prompts/generator.py:847-869](../../../../rag/prompts/generator.py#L847-L869)

```python
async def relevant_chunks_with_toc(query: str, toc: list[dict], chat_mdl, topn: int=6):
    import numpy as np
    try:
        # 1. 构建LLM输入
        ans = await gen_json(
            PROMPT_JINJA_ENV.from_string(TOC_RELEVANCE_SYSTEM).render(),
            PROMPT_JINJA_ENV.from_string(TOC_RELEVANCE_USER).render(
                query=query,
                toc_json="\n".join([
                    json.dumps({
                        "level": d["level"],
                        "title": d["title"]
                    }, ensure_ascii=False)
                    for d in toc
                ])
            ),
            chat_mdl,
            gen_conf={"temperature": 0.0, "top_p": 0.9}
        )

        # 2. 聚合分数到chunks
        id2score = {}
        for ti, sc in zip(toc, ans):
            if not isinstance(sc, dict) or sc.get("score", -1) < 1:
                continue
            for id in ti.get("ids", []):
                if id not in id2score:
                    id2score[id] = []
                id2score[id].append(sc["score"]/5.)  # 归一化到 [0, 1]

        # 3. 计算平均分数
        for id in id2score.keys():
            id2score[id] = np.mean(id2score[id])

        # 4. 过滤并排序
        return [(id, sc) for id, sc in list(id2score.items()) if sc >= 0.3][:topn]
    except Exception as e:
        logging.exception(e)
    return []
```

**评分系统**：

| 分数 | 含义 | 说明 |
|------|------|------|
| **5** | 高度相关 | 直接回答或匹配查询意图 |
| **3** | 中度相关 | 相同主题或部分重叠 |
| **1** | 弱相关 | 模糊或边缘相关 |
| **0** | 无明显关系 |
| **-1** | 明确不相关 | 矛盾或无关 |

```markdown
- 5 → highly relevant (directly answers or matches the query intent)
```

**功能说明**：

**为什么使用0.3作为阈值？**

1. **归一化分数**
   - LLM评分：1-5
   - 归一化：0.2-1.0 (除以5)
   - 阈值0.3对应LLM评分1.5

2. **平衡召回和精度**
   - 0.3：包含弱相关但可能有用的内容
   - 避免过度召回（包含太多无关内容）

3. **经验值**
   - 基于实际测试调整
   - 适应大多数场景

### 步骤5: 加载新chunks并更新相似度 (673-701行)

```python

        "chunk_id": cid,
        "content_ltks": chunk["content_ltks"],

        "docnm_kwd": chunk.get("docnm_kwd", ""),
        "kb_id": chunk["kb_id"],
        "important_kwd": chunk.get("important_kwd", []),
        "image_id": chunk.get("img_id", ""),
        "similarity": sim,
        "vector_similarity": sim,
        "term_similarity": sim,
        "vector": [0.0] * vector_size,
        "positions": chunk.get("position_int", []),
        "doc_type_kwd": chunk.get("doc_type_kwd", "")

    for k in chunk.keys():
```

**功能说明**：
- 遍历TOC评估发现的相关chunks
- 如果chunk已存在：增加其相似度（奖励）
- 如果chunk不存在：从数据库加载并添加

**两种情况处理**：

**情况1: chunk已存在**

```python
# 原始chunks
chunks = [
    {"chunk_id": "ch_1", "similarity": 0.82, ...},
    {"chunk_id": "ch_2", "similarity": 0.78, ...},
    {"chunk_id": "ch_3", "similarity": 0.75, ...}
]

# TOC发现的相关chunks
ids = [("ch_1", 0.6), ("ch_4", 0.9), ("ch_5", 0.8)]

# 处理
id2idx = {"ch_1": 0, "ch_2": 1, "ch_3": 2}

# ch_1: 已存在
if "ch_1" in id2idx:
    chunks[0]["similarity"] += 0.6
    # chunks[0]["similarity"] = 0.82 + 0.6 = 1.42

# ch_4: 不存在，加载并添加
# ch_5: 不存在，加载并添加
```

**情况2: chunk不存在**

```python

# 返回: {"chunk_id": "ch_4", "content_ltks": "...", "q_1024_vec": [...], ...}

# 构建新的chunk对象
d = {
    "chunk_id": "ch_4",
    "content_ltks": "...",
    "similarity": 0.9,  # TOC评估分数
    "vector_similarity": 0.9,
    "term_similarity": 0.9,
    "vector": [...],  # 从chunk中提取
    ...
}

# 添加到chunks列表
chunks.append(d)
```

**向量字段提取**：

```python
# 尝试提取向量字段
for k in chunk.keys():
    if k[-4:] == "_vec":  # 匹配 "*_vec" 后缀
        d["vector"] = chunk[k]
        vector_size = len(chunk[k])
        break
```

**示例**：

```python

chunk = {
    "chunk_id": "ch_4",
    "content_ltks": "...",
    "q_1024_vec": [0.1, 0.2, ..., 0.8],  # 1024维向量
    "q_768_vec": [0.3, 0.4, ..., 0.9],   # 768维向量
    ...
}

# 提取向量（找到第一个匹配）
for k in chunk.keys():
    if k[-4:] == "_vec":
        if k == "q_1024_vec":  # 第一个匹配
            d["vector"] = chunk["q_1024_vec"]
            vector_size = 1024
            break
```

### 步骤6: 排序并返回top-n (703行)

```python
return sorted(chunks, key=lambda x:x["similarity"]*-1)[:topn]
```

**功能说明**：
- 按相似度降序排序
- 返回前n个结果

**示例**：

```python

chunks = [
    {"chunk_id": "ch_1", "similarity": 1.42},  # 0.82 + 0.6 (TOC奖励)

sorted_chunks = [
    {"chunk_id": "ch_1", "similarity": 1.42},  # 第1名

    {"chunk_id": "ch_5", "similarity": 0.8},   # 第3名 ⭐
    {"chunk_id": "ch_2", "similarity": 0.78},
    {"chunk_id": "ch_3", "similarity": 0.75}
]

# 返回前6个（假设topn=6）
return sorted_chunks[:6]
```

## 🎯 关键设计决策

### 1. 为什么只选择一个文档的TOC？

**当前实现**：
```python
doc_id = sorted(ranks.items(), key=lambda x: x[1]*-1.)[0][0]
```

**原因**：

1. **性能考虑**
   - LLM评估TOC是昂贵操作
   - 只处理最相关的文档
   - 减少计算开销

2. **效果考虑**
   - 最相关的文档通常包含所需信息
   - 多文档场景可以通过多轮检索处理

3. **简化逻辑**
   - 避免跨文档的TOC合并
   - 便于实现和维护

**潜在改进**：
```python
# 选择top-2文档的TOC
doc_ids = sorted(ranks.items(), key=lambda x: x[1]*-1.)[:2]
for doc_id in doc_ids:
    # 处理每个文档的TOC
```

### 2. 为什么使用LLM而不是规则匹配？

**LLM方式（当前）**：
```python
ans = await gen_json(..., chat_mdl, ...)
```

**规则方式（替代方案）**：
```python
# 关键词匹配
for toc_item in toc:
    if any(keyword in toc_item["title"] for keyword in query_keywords):
        score = 5
```

**选择LLM的原因**：

1. **语义理解**
   - LLM能理解查询的深层意图
   - 规则匹配只能处理字面匹配

2. **层级推理**
   - LLM能理解父子章节的关系
   - 规则匹配难以处理层级结构

3. **灵活性**
   - LLM适应各种查询场景
   - 规则匹配需要人工设计规则

**示例对比**：

```python
# 查询: "深度学习在图像识别中的应用"

# TOC条目: "计算机视觉技术"

# 规则匹配
if "图像识别" in "计算机视觉技术":
    score = 5  # False，不匹配

# LLM评估
# LLM知道"计算机视觉"包含"图像识别"
score = 5  # True，匹配
```

### 3. 为什么要增加已存在chunks的相似度？

**当前实现**：
```python
if cid in id2idx:
    chunks[id2idx[cid]]["similarity"] += sim
```

**原因**：

1. **奖励机制**
   - 初始检索和TOC评估都认为相关
   - 双重验证，应该提升排名

2. **避免重复**
   - 不添加重复的chunk
   - 只调整相似度

3. **权重平衡**
   - 初始相似度 + TOC分数
   - 综合两个信号

**数值示例**：

```python
# 场景1: 初始检索认为相关，TOC也认为相关
initial_similarity = 0.8
toc_score = 0.9
final_similarity = 0.8 + 0.9 = 1.7  # 大幅提升

# 场景2: 初始检索认为相关，TOC认为不相关
initial_similarity = 0.8
toc_score = 0  # 不会被添加
final_similarity = 0.8  # 保持不变
```

### 4. 为什么TOC分数作为similarity/vector_similarity/term_similarity？

**当前实现**：
```python
d = {
    "similarity": sim,
    "vector_similarity": sim,
    "term_similarity": sim,
    ...
}
```

**原因**：

1. **简化实现**
   - TOC分数是一个综合评分
   - 难以分离向量/词元相似度

2. **避免混淆**
   - 新chunks没有原始的向量/词元相似度
   - 使用TOC分数作为替代

3. **统一接口**
   - 保持与初始检索结果相同的字段结构
   - 便于后续处理

## 📈 总结

`retrieval_by_toc()` 是 RAGFlow 系统中的**TOC增强检索功能**，通过利用文档的结构化目录信息来提升检索精度。

### 核心功能

1. **文档选择**: 基于初始检索选择最相关文档
2. **TOC加载**: 从数据库加载文档的结构化目录
3. **LLM评估**: 使用LLM评估TOC条目与查询的相关性
4. **分数聚合**: 将TOC评分转换为chunk相似度
5. **chunks加载**: 加载新发现的chunks并更新相似度
6. **结果排序**: 按相似度排序并返回top-n

### 关键技术

1. **层级TOC理解**: LLM理解文档的层级结构
2. **语义相关性评估**: 基于LLM的深度语义匹配
3. **双重验证机制**: 初始检索 + TOC评估
4. **相似度奖励**: 对双重验证的chunks提升相似度

### 业务价值

- **提升召回率**: 发现初始检索遗漏的相关内容
- **结构化理解**: 利用文档的层级结构
- **语义匹配**: 基于LLM的深度语义理解
- **灵活适应**: 适用于各种结构化文档
